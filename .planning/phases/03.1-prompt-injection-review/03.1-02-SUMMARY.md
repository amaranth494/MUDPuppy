# Phase 3.1 Plan 02: Never-Issue List Storage and Settings Field Summary

**Owner-editable Never-Issue List column, AI-settings sub-resource field with a 20,000-char cap, and a settings textarea beside Conduct Rules and Approach Guidance, all empty by default and round-tripping through the existing profile save/load path.**

## Performance

- **Duration:** 55 min
- **Started:** 2026-09-16T11:03:00Z (approx, worktree branch-check/context-read start)
- **Completed:** 2026-09-16
- **Tasks:** 3
- **Files modified:** 7 (2 new migration files, 5 modified source files)

## Accomplishments
- Migration `012` adds `profiles.never_issue_list TEXT NOT NULL DEFAULT ''` and widens the `ai_decisions.outcome` CHECK to admit `'blocked'`, using a name-agnostic `pg_constraint` lookup rather than a guessed constraint name (the original CHECK in migration 011 is inline and unnamed)
- `internal/store/profile.go`'s `Profile`/`ProfileUpdate` structs, both `GetProfile*` readers, and `UpdateProfile` all carry `NeverIssueList` as a third sibling of `ConductRules`/`ApproachGuidance`, with the `UPDATE` statement's placeholders renumbered consistently
- `internal/profiles/handler.go`'s `AISettingsResponse`, `GetAISettings`, and `PutAISettings` carry `never_issue_list`; `validateAISettings` rejects lists over 20,000 characters with the exact message `Never-issue list must be 20000 characters or less`
- `TestAISettingsRoundTrip` now asserts an empty `never_issue_list` on a freshly built profile before any PUT (the empty-by-default guarantee, D-02), then a two-line value round-tripping unchanged after PUT/GET; `TestAISettingsRejectsOverLengthNeverIssueList` covers the cap and asserts no store update was recorded
- The AI Player settings panel gained a `Never-Issue List` textarea (120px min-height, matching its two siblings) between Approach Guidance and Model Name, with the locked hint copy reproduced character for character, saved by the existing shared "Save AI Settings" button

## Decisions Made
- The 20,000-character cap matches its two siblings exactly rather than introducing a new number, per 03.1-UI-SPEC.md's locked reuse decision (overriding 03.1-RESEARCH.md's 5,000 suggestion, Assumption A2).
- Migration 012 carries both this phase's schema changes in one file (the profile column and the outcome CHECK widening) even though `blocked` is not written until plan 03.1-03, per the orchestrator's stated no-speed-bumps rationale in the plan objective.
- No fallback `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` was added to `cmd/server/main.go` — that pattern is reserved for migrations 009/010 which predate current packaging; migration 011 applied cleanly from `file://migrations` without one, so 012 is expected to as well.
