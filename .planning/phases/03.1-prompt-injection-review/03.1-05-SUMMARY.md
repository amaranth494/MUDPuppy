# Phase 3.1 Plan 05: Blocked Decision Rendering in the AI Assist Panel and Terminal Summary

**A fourth `blocked` outcome renders as a warning-bordered decision card with the attempted command and reason (live and after reload), plus one brightyellow bracketed terminal line — closing RESEARCH Pitfall 5's reload-drops-the-command bug along the way.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2
- **Files modified:** 4

## Accomplishments

- `AIDecisionPayload.outcome` (`frontend/src/types/index.ts`) now admits `'blocked'` as a fourth union member; no new field was added — the existing optional `message` carries the reason, exactly as the server sends it.
- `AIAssistPanel.tsx`'s `DecisionEntry` gained an optional `reason?: string`. `loadHistory`'s reload mapping was rewritten from a two-way ternary (`item.outcome === 'sent' ? item.command : item.notice`) to the UI-spec's three-way branch: the command slot takes the stored notice only for `failed`/`refused`, and keeps the real command for both `sent` and `blocked`; `reason` is populated from `item.notice` only when the outcome is `blocked`. This is the Pitfall 5 fix — before this change, a reloaded blocked row would have shown the reason in place of the command, hiding the very thing the phase exists to show.
- `handleAI`'s live-push decision branch populates `reason` from `payload.message` only when `payload.outcome === 'blocked'`, leaving every other outcome's live-push shape untouched.
- The decision-card JSX renders `Blocked → {command}` when the outcome is `blocked` (and the unchanged `→ {command}` otherwise), plus a conditional `<div className="ai-decision-blocked-reason">` sibling that only appears when the outcome is `blocked` and a reason string is present. The existing `` `ai-decision outcome-${entry.outcome}` `` class expression already yields `outcome-blocked` — no class-name logic changed.
- `PlayScreen.tsx`'s `handleAI` gained a third branch, inserted between the existing `sent` and `system` branches: on a decision-kind payload with outcome `blocked`, it calls `automationEngine.echoLocal` with `` `[AI-ASSIST blocked > ${payload.command}]` `` in `brightyellow` — command only, never the reason, matching every other bracketed terminal notice's one-line discipline. The two existing branches (`sent`/`brightmagenta`, `system`/`red`) are byte-for-byte unchanged.
- `index.css` gained exactly three rules immediately after the existing `.ai-decision.outcome-failed`/`.outcome-refused` rule: a 2px `--color-warning` left border on `.ai-decision.outcome-blocked`, a `--color-warning` override on that card's `.ai-decision-command`, and `.ai-decision-blocked-reason`'s `--font-size-sm`/`--color-text-dim`/`--spacing-xs`-top-margin styling. All four custom properties referenced already existed in the file before this plan; no new custom property was declared and the only pixel literal (`2px`) was already in use elsewhere in the file.

## Old vs. New Reload Mapping (Pitfall 5 audit trail)

```tsx
// OLD (frontend/src/components/AIAssistPanel.tsx, loadHistory, before this plan):
command: item.outcome === 'sent' ? item.command : item.notice,
// A reloaded blocked row would have fallen into the ": item.notice" branch,
// showing the reason string in the command slot and losing the attempted
// command entirely — only visible after a page refresh, never live.

// NEW (this plan):
command: item.outcome === 'failed' || item.outcome === 'refused' ? item.notice : item.command,
reason: item.outcome === 'blocked' ? item.notice : undefined,
// 'sent' and 'blocked' both keep the real command in the command slot;
// 'failed'/'refused' are unchanged (notice in the command slot, as before);
// 'blocked' additionally carries the reason in its own field.
```

## Decisions Made

- Kept the reload mapping as a single three-way ternary plus a separate `reason` assignment rather than a four-branch switch, matching the UI-spec's locked code example exactly and keeping the diff minimal against the existing one-line ternary.
- `reason` is `undefined` (not an empty string) for every non-blocked outcome, so the `entry.outcome === 'blocked' && entry.reason` JSX guard is a clean falsy check with no empty-`<div>` edge case.
