## Unregistered Attack Surface (found during verification, no `T-3.1-NN` mapping)

These did not appear in any plan's `<threat_model>` block. They are new findings surfaced by code review or by the staging walkthrough itself, both of which are already on `03.1-SECURITY-AGENDA.md` for the owner's disposition — they are listed here because the audit's job is to say plainly that they were never part of the declared register, not to imply they are unhandled.

1. **Agenda Item 6 — the staging credential vault key was ephemeral (`ENCRYPTION_KEY_V1` unset on staging).** `internal/crypto.DefaultKeyStore` (`internal/crypto/crypto.go:27-49`) silently generates a random key on every process start when no environment key is configured, with a "for development only" comment that no code path enforces. This made every stored MUD password on staging undecryptable after each redeploy and, during walkthrough 2, let autopilot answer a character-creation prompt (`yes`) it was never meant to see (`evidence/06-staging-ai-player.log:93-97`, stopped by `#AUTO OFF` before a character was created). This is infrastructure, not Phase 3.1's own code, and has no `T-3.1-NN` id — it is carried to `03.1-SECURITY-AGENDA.md` Item 6 with three dispositions, unchecked. **WARNING, unregistered_flag.**
2. **WR-02 — the down migration cannot roll back once any `blocked` row exists.** `migrations/012_..._down.sql` unconditionally re-adds the three-value `CHECK`; confirmed by direct read that no `UPDATE ai_decisions SET outcome='failed' WHERE outcome='blocked'` (or equivalent neutralization/warning) precedes it. This is an operational/rollback-safety gap distinct from T-3.1-08 (which is about the *up* migration's constraint-name robustness, already closed). Not on any agenda item as of this audit. **WARNING, unregistered_flag.**
3. **WR-03 — the owner-facing Never-issue hint and the model-facing system-instruction sentence both describe the matcher slightly more generously than `matchNeverIssue` implements** (e.g., "whole-word" phrasing beside a matcher that is a prefix-plus-space/exact match with no punctuation awareness — `give,` would not be caught by an entry `give`). This is a documentation-precision gap around an already-correct, already-tested control (T-3.1-03/D-02), not a new code vulnerability. **INFO**, not a blocker.
