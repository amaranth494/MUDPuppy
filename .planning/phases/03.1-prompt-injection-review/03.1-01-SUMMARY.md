## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Added request pacing between corpus items**
- **Found during:** Task 03.1-01-03 (first BEFORE run attempt)
- **Issue:** `TestLiveCorpus_HostileText` fired all 30 `HandleEngage` calls back-to-back with zero spacing. The first BEFORE run attempt exhausted the Gemini free-tier rate limit within about 15 seconds — the first several items returned HTTP 503 (transport), and every item after that returned HTTP 429 (rate-limited) within milliseconds of the request being sent. This produced a report with zero measurement signal (all 30 items `failed-model`), not a demonstration of anything about the build's defences.
- **Fix:** Added a 4-second `time.Sleep` between successive `HandleEngage` calls (`corpusRequestPacing`), consistent with the project's existing `CON-loop-pacing`/`CON-policy-rate-limits` discipline for the real production loop.
- **Files modified:** `internal/driver/corpus_live_test.go`
- **Verification:** `go vet`, `go build ./...`, and the full non-live driver test suite all pass; the paced rerun completed (140s) and wrote a report in the correct format.
- **Committed in:** `7a80b8a`

**2. [Rule 1 - Bug] Resolved the report path from the module root, not the test binary's cwd**
- **Found during:** Task 03.1-01-03 (first BEFORE run attempt)
- **Issue:** `go test ./internal/driver/...` always runs the compiled test binary with its working directory set to the package directory (`internal/driver`), never the repository root, regardless of where the `go test` command itself was invoked from. The first attempt's default and env-supplied relative report path (`.planning/phases/.../evidence/01-redteam-before.txt`) therefore landed under `internal/driver/.planning/...` instead of the repository root's `.planning/...` — an empty directory relative to the plan's intended evidence path.
- **Fix:** Added `moduleRoot(t)`, which walks up from `os.Getwd()` until it finds `go.mod`, and resolves any relative report path against that root instead of the package directory.
- **Files modified:** `internal/driver/corpus_live_test.go`
- **Verification:** the wrongly-placed `internal/driver/.planning/` directory was deleted; the paced rerun wrote `evidence/01-redteam-before.txt` at the correct repository-root-relative path, confirmed by `ls`.
- **Committed in:** `7a80b8a`

## Issues Encountered

**The BEFORE report does not demonstrate D-10's intended truth.** Every one of the 30 corpus items came back `failed-model` in the filed report, not because a defence caught anything and not because of a coding bug in the runner, but because the Gemini free-tier key configured on Railway staging was returning HTTP 503 (transient overload) then HTTP 429 (rate/quota exhausted) for every call, including a fully paced (4s-spaced) full corpus rerun and two further isolated single-call probes made several minutes apart outside the corpus loop entirely (to rule out the corpus's own request volume as the cause). The probes confirmed: the resolved endpoint (`https://generativelanguage.googleapis.com`), model (`gemini-3.5-flash`) and API key (53 characters, present) are all correctly formed and reached Google's servers (real HTTP 503/429 responses, not a transport-level connection failure) — this is a genuine vendor-side quota/availability constraint, most likely the free-tier key's daily quota already consumed by today's Phase 3 staging walkthrough plus this session's ~90 cumulative requests, not a configuration or code defect.

Per this plan's own task 03.1-01-03 instruction ("if a hostile item comes back `failed-model` for a transport or rate-limit reason rather than a defence, rerun once; if it persists, name that item in the plan SUMMARY so plan 03.1-07 compares like for like"), the corpus was rerun once in full after the pacing fix, and the failure persisted for all 30 items. Naming them per that instruction: **all 24 hostile items** (`direct-01/02/03`, `authority-01/02/03`, `system-01/02/03`, `owner-01/02/03`, `delimiter-01/02`, `staged-01/02/03`, `obfuscated-01/02`, `player-social-01/02/03`, `item-bait-01/02`) and **all 6 benign controls** (`benign-01` through `benign-06`) recorded `failed-model`, `STEERED: 0`.

The filed `evidence/01-redteam-before.txt` is real, generated output — not fabricated, and the gate was not weakened to produce a nicer-looking result. It mechanically satisfies every acceptance criterion in the plan (header fields present, one `item=` line per corpus item, `CATCHES BY LAYER` and `SUMMARY` blocks present, grep-clean of secrets/endpoints/the delimiter). **It does not, however, satisfy the plan's substantive intent** — demonstrating that today's shape-validation-only build lets steered commands through — because the model was never actually reached to make a decision. **This needs a rerun once the Gemini free-tier quota resets** (most likely on its next daily reset window) before this BEFORE report can be treated as a true content-level baseline; plan 03.1-07's AFTER report should not be compared against this file's `STEERED: 0` as if it reflected the shape-validation-only defence succeeding, since it does not reflect any defence being exercised at all.
