# Phase 3.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope actually covered here** (per orchestrator instruction — nothing else is in Phase 3.1 UI):
(a) the **Never-Issue List** text box in the AI Player settings section, beside Conduct Rules and Approach Guidance;
(b) the **blocked decision** rendering in the AI Assist panel — reasoning, attempted command, and block reason — visually distinct from a sent decision and from a D-13 failure/refusal notice, identical whether live-pushed or reloaded after a refresh;
(c) the **terminal line** for a block through the local-echo path;
(d) the fact that a block leaves the autopilot indicator ON with no badge change, and the (absence of) copy that states that;
(e) which existing D-13 failure notice wording each reviewer-failure kind reuses;
(f) the regression invariant, extended to cover the Never-Issue list and the reviewer pass;
(g) every new copy string this phase introduces, locked verbatim.

This phase adds **zero** new CSS custom properties. It reuses Phase 3's `--color-ai-accent`, `--color-warning`, `--color-error`, and the existing spacing scale exactly as they stand. No component library, no shadcn — unchanged from Phases 1-3.

## Color

Existing tokens in `index.css`, reused as-is — no new custom properties this phase:

| Role | Value | Usage in this phase |
|------|-------|-----------|
| Accent (10%, AI identity) | `#ff66ff` (`--color-ai-accent`) | Unchanged — still reserved for sent AI commands only (`→ {command}` in the panel, `[AI-ASSIST > {command}]` in the terminal/transcript). **Never used for a blocked command** — a block is not a successful AI-identity event. |
| Warning | `#ffff00` (`--color-warning`) | **Reused for a second, closely-related semantic:** the blocked command line, the blocked card's left border, and the `[AI-ASSIST blocked > {command}]` terminal line (`brightyellow`). Justified below. |
| Destructive | `#ff4444` (`--color-error`) | Unchanged — still reserved for every disengage/refusal/failure notice, including the three D-13 notices the reviewer-failure path reuses verbatim (see Copywriting Contract). **Never used for a block** — D-06 makes a block explicitly not a failure. |
| Text-dim | `var(--color-text-dim)` | Unchanged — the blocked reason line and the blocked card's reasoning paragraph both use it, exactly like every other decision card. |

### Why `--color-warning` is reused for "blocked," not a new token

Scope requires reusing Phase 3's AI-identity accent and the existing scale, adding nothing new unless justified. A block is neither the AI-identity green-adjacent "success" signal (`--color-ai-accent`, reserved for a command that was actually sent) nor a failure (`--color-error`, reserved for "autopilot disengaged"). It shares its true semantic with exactly one existing reservation: `--color-warning`, already defined as "autopilot is still ON/engaged, but not currently acting" (the WAITING system line, D-11 carried from Phase 2). A block is the decision-level instance of that same fact — the switch stays ON and idle (D-06) — so extending the same colour to a second, semantically identical state is the reuse the scope note asks for, not scope creep. `--color-ai-accent` and `--color-error` keep their existing, narrower reservations unchanged.

## Copywriting Contract

Plain, non-marketing, terminal-friendly — matches the existing voice and Phase 1/3's contracts. Every string below is new to this phase and locked verbatim; everything not listed is unchanged from `03-UI-SPEC.md`.

| Element | Copy |
|---------|------|
| Never-Issue List — field label | `Never-Issue List` |
| Never-Issue List — placeholder | *(none — textarea, matching Conduct Rules and Approach Guidance exactly)* |
| Never-Issue List — hint | `One entry per line. A command is blocked if it starts with an entry, matched whole-word and case-insensitive — so "give" blocks "give sword to bob" but not "giveaway". Blank means none: nothing is blocked by this list, though the reviewer and the model's own judgment still apply.` |
| Panel — blocked command line | `Blocked → {command}` (Body-bold, `--color-warning`; visually parallels the sent line's `→ {command}` in AI-accent, but a different lead word and a different colour make the two impossible to confuse at a glance) |
| Panel — blocked reason line, Never-Issue layer | `Matched Never-issue entry: "{entry}"` (Label, `--color-text-dim`) |
| Panel — blocked reason line, reviewer layer | `Reviewer blocked: {verdict}` (Label, `--color-text-dim`; `{verdict}` is the reviewer's one-sentence reason from its JSON answer, shown verbatim, no paraphrasing) |
| Terminal — blocked command echo | `[AI-ASSIST blocked > {command}]` (verbatim format; `brightyellow`/`--color-warning`; e.g. `[AI-ASSIST blocked > give sword to bob]`) — names the command only, never the reason (the reason lives in the panel; the terminal stays one line, matching every other bracketed notice's length) |
| Autopilot state after a block | **No new copy.** The `AutopilotBadge` and the terminal's `[Autopilot engaged]` system line are untouched by a block — no line is printed and no badge state changes. The absence of a disengage notice is itself the signal that autopilot remains ON and idle (D-06); inventing a reassurance string here would be exactly the "speed bump" plumbing-as-decision the project avoids. |
| Reviewer-failure notices | **No new copy.** When the reviewer call itself fails (D-09: unreachable, rate limited, unreadable answer), the driver disengages and the existing D-13 notice for that failure kind is reused verbatim, unchanged from `03-UI-SPEC.md`, in both the panel and the terminal — the string never states which of the two Gemini calls (player or reviewer) failed, consistent with D-13's existing "plain, no vendor-call internals" voice: <br>• unreachable → `[AI decision failed: the model could not be reached. Autopilot disengaged.]` <br>• rate limited → `[AI decision failed: the model's rate limit was reached. Autopilot disengaged.]` <br>• unreadable/malformed verdict → `[AI decision failed: the model's answer could not be understood. Autopilot disengaged.]` <br>The other three D-13 kinds (no command, multiple commands, non-game line) are player-call-only shape checks and do not apply to the reviewer stage. |
| Destructive confirmation | None in this phase. Editing or clearing the Never-Issue List is a plain text edit saved by the same non-destructive "Save AI Settings" button as its siblings — no delete action, no confirmation dialog. |

## Layout & Component Reuse

### 1. Never-Issue List field (`frontend/src/components/AIPlayerPanel.tsx`, extended)

New state, positioned in the component's field-state block immediately after `approachGuidance`:
```tsx
const [neverIssueList, setNeverIssueList] = useState('');
```
Read/write it in `applyAISettings` and the `handleSave` body payload the same way `conduct_rules`/`approach_guidance` already are (field key follows the same snake_case convention, e.g. `never_issue`; exact backend column/JSON name is the executor's discretion per 03.1-CONTEXT.md, not a UI concern).

Markup, inserted between the Approach Guidance `.form-group` and the Model Name `.form-group` — i.e. immediately after line 224, before line 226 in the current file — so the three model-facing text fields (Conduct Rules, Approach Guidance, Never-Issue List) read as one visual group ahead of the numeric AI settings fields, satisfying D-02's "beside conduct rules and approach guidance":

```tsx
<div className="form-group">
  <label className="form-label">Never-Issue List</label>
  <textarea
    className="form-input form-textarea"
    style={{ minHeight: '120px' }}
    value={neverIssueList}
    onChange={(e) => setNeverIssueList(e.target.value)}
  />
  <p className="form-hint">
    One entry per line. A command is blocked if it starts with an entry, matched
    whole-word and case-insensitive — so &quot;give&quot; blocks &quot;give sword to bob&quot;
    but not &quot;giveaway&quot;. Blank means none: nothing is blocked by this list, though
    the reviewer and the model&apos;s own judgment still apply.
  </p>
</div>
```

No new CSS classes — `.form-group`, `.form-label`, `.form-input.form-textarea`, `.form-hint` are the exact classes Conduct Rules and Approach Guidance already use (`AIPlayerPanel.tsx` lines 204-224). Save behaviour is identical to the sibling fields: one shared `handleSave`, one shared `.settings-actions` "Save AI Settings" button, one shared `Saving…` disabled state, one shared success/error message — no separate save action, no separate loading state for this field alone.

Length limit: reuses the exact same `validateUpdate` character-limit constant already enforced on Conduct Rules (20,000 characters) rather than a new value — the field's discretion note asks for "the existing `validateUpdate` style," which is reuse, not a new number. The limit is **not displayed** in the hint text, matching the sibling fields, which also don't surface their limit in copy.

### 2. Blocked decision card (`frontend/src/components/AIAssistPanel.tsx`, extended)

`DecisionEntry.outcome` gains a third real value, `'blocked'`, alongside the existing `'sent'`/`'failed'`/`'refused'` strings already flowing through this component. A blocked event is a **decision**, not a **system** entry (D-08: "stored as its own decision row") — it must render through the same `ai-decision` card path as a sent decision, never through the ephemeral `ai-system-line` path used for failure/refusal notices.

**Live push** (`handleAI`, lines 78-104): the `'blocked'` outcome arrives on a `kind: 'decision'` payload exactly like `'sent'`, carrying `reasoning`, `command`, and a reason string. This phase reuses the existing `AIDecisionPayload.message` field (already defined for `kind: 'system'` payloads) to carry the reason on a `kind: 'decision', outcome: 'blocked'` payload too, rather than adding a new field — the same "extend before invent" reuse discipline this contract already applies elsewhere. `AIDecisionPayload.outcome`'s TypeScript union (`frontend/src/types/index.ts` line 79) extends from `'sent' | 'refused' | 'failed'` to `'sent' | 'refused' | 'failed' | 'blocked'`.

**Reload mapping** (`loadHistory`, lines 51-72): the current ternary (`command: item.outcome === 'sent' ? item.command : item.notice`) collapses the command and the notice into one slot, which is correct for `'failed'`/`'refused'` (where only the notice matters) but wrong for `'blocked'` (where both the real attempted command and the reason must show). This phase changes the mapping to a three-way branch:

```tsx
const mapped: PanelEntry[] = stored.map((item) => ({
  kind: 'decision',
  id: item.id,
  reasoning: item.reasoning,
  command: item.outcome === 'failed' || item.outcome === 'refused' ? item.notice : item.command,
  reason: item.outcome === 'blocked' ? item.notice : undefined,
  outcome: item.outcome,
}));
```

`DecisionEntry` gains an optional `reason?: string` field, populated from `StoredDecision.notice` on reload and from `AIDecisionPayload.message` on a live push — no new API field name, `notice`/`message` already exist and already carry exactly this kind of human-readable string for the other two non-sent outcomes.

**Because a blocked row is a genuine stored decision (not a live-only system line), it renders pixel-identical whether it just happened live or was reloaded after a page refresh** — this is the visual proof for D-08's "reloads into the AI Assist panel after a page refresh" requirement, and the reason this phase does not need a separate "reload state" for blocked entries the way system lines explicitly don't survive a reload.

**Markup** (extends the existing decision-card render, lines 156-160):
```tsx
entry.kind === 'decision' ? (
  <div key={key} className={`ai-decision outcome-${entry.outcome}`}>
    <div className="ai-decision-reasoning">{entry.reasoning}</div>
    <div className="ai-decision-command">
      {entry.outcome === 'blocked' ? `Blocked → ${entry.command}` : `→ ${entry.command}`}
    </div>
    {entry.outcome === 'blocked' && entry.reason && (
      <div className="ai-decision-blocked-reason">{entry.reason}</div>
    )}
  </div>
) : ( /* unchanged system-line branch */ )
```

**CSS** (`frontend/src/index.css`, appended immediately after the existing `.ai-decision.outcome-failed`/`.outcome-refused` rule at line 331):
```css
.ai-decision.outcome-blocked {
  border-left: 2px solid var(--color-warning);
}
.ai-decision.outcome-blocked .ai-decision-command {
  color: var(--color-warning);
}
.ai-decision-blocked-reason {
  font-size: var(--font-size-sm);
  color: var(--color-text-dim);
  margin-top: var(--spacing-xs);
}
```

No change to `.ai-decision-reasoning` — a blocked card's reasoning paragraph stays the same dim body text every other decision card uses; only the command line and the new reason line carry the warning colour.

**Whether the panel labels which layer caught it:** resolved by the reason string's own wording, not a separate UI element — `Matched Never-issue entry: "{entry}"` and `Reviewer blocked: {verdict}` are each self-describing, so no extra "layer" badge or icon is needed (03.1-CONTEXT.md leaves this open; this is the simplest thing that satisfies it, consistent with "no speed bumps").

### 3. Terminal blocked echo (`frontend/src/pages/PlayScreen.tsx`, extended)

`handleAI` (lines 415-421) gains a third branch, inserted between the existing `sent` branch and the `system` branch:
```tsx
if (payload.kind === 'decision' && payload.outcome === 'sent') {
  automationEngine.echoLocal(`[AI-ASSIST > ${payload.command}]`, { color: 'brightmagenta' });
} else if (payload.kind === 'decision' && payload.outcome === 'blocked') {
  automationEngine.echoLocal(`[AI-ASSIST blocked > ${payload.command}]`, { color: 'brightyellow' });
} else if (payload.kind === 'system') {
  automationEngine.echoLocal(`[${payload.message}]`, { color: 'red' });
}
```
`brightyellow` is the exact ANSI colour name already used for `[Autopilot waiting for reconnect]` (line 397) — the same reuse justified in the Color section above, applied consistently to the terminal surface. This line reads no cyan (human-typed), no magenta (AI-sent), no red (failed/refused) — it cannot be mistaken for a typed echo or an existing failure notice, satisfying D-09's "never look alike" carried into this phase's scope.

## Regression Invariant (carries Phase 2 D-12 and Phase 3's invariant forward, non-negotiable)

For any profile that has **not** accepted the Phase 1 policy: unchanged from `03-UI-SPEC.md` — no AI Assist panel, no `--color-ai-accent`/`--color-warning` terminal line, no Never-Issue List field even rendered (the whole AI Player settings body, including this new field, only renders once `policy.accepted` is true, exactly like Conduct Rules and Approach Guidance already do).

For any profile that **has** accepted the policy:
- With autopilot never engaged, or engaged with no block ever having occurred: the panel shows only its existing empty state or existing sent/failed/refused cards; `.outcome-blocked` and `.ai-decision-blocked-reason` never render, and the terminal never prints a `brightyellow` `[AI-ASSIST blocked > ...]` line. The Never-Issue List field is present (empty by default, D-02) but inert until a command is actually blocked.
- **Hand play is entirely unaffected.** The Never-Issue List, the reviewer pass, and every string in this contract apply exclusively to AI-issued decisions on the automation path (D-04's shape-validation → Never-Issue → reviewer → dispatch order). A human typing a command directly — including typing the exact text of a Never-Issue entry — is never checked against this list and never triggers a `blocked` outcome; the wheel-grab and ordinary command echo behave exactly as Phase 2 left them.
- Ordinary connect, disconnect, the autopilot badge, and every Phase 2/3 bracketed notice are unchanged in appearance and colour.

## Claude's Discretion (visual contract only — does not change owner-visible behavior)

- **`--color-warning` reused for the blocked state rather than a new token** — justified above under Color; both states share the identical underlying fact ("autopilot remains ON, not currently acting").
- **Never-Issue List field position** (between Approach Guidance and Model Name) — D-02 only locks "beside conduct rules and approach guidance"; grouping the three model-facing text fields together, ahead of the numeric AI settings fields, is the chosen reading of that instruction.
- **Never-Issue List textarea height (120px)** — reuses the sibling fields' exact value rather than a new one, so the three fields read as one visual group.
- **Never-Issue List matching-rule wording in the hint** (case-insensitive, whole-word boundary, blank-line-safe) — D-02 locks the prefix-match behavior ("`give` blocks `give sword to bob`"); the whole-word-boundary refinement (so `give` does not block `giveaway`) is 03.1-CONTEXT.md's own discretion note, resolved here in the simplest way that satisfies it and stated in copy so the owner understands the box's actual behavior.
- **Length limit reused from `validateUpdate`'s existing 20,000-character constant, not displayed in copy** — matches sibling field behavior exactly; no new number introduced.
- **`Blocked → {command}` / reason-line wording and layout** — D-07 locks the content (command plus reason, visually distinct from sent); the exact two-line card layout, the lead word "Blocked," and the arrow-reuse for visual parallelism with the sent card are this phase's chosen realization.
- **Two reason-string templates carrying the layer name implicitly** (`Matched Never-issue entry: "..."` / `Reviewer blocked: ...`) rather than a separate layer badge — 03.1-CONTEXT.md explicitly leaves "whether the panel shows which layer caught it" open; folding it into the reason string is the simplest resolution.
- **Terminal line `[AI-ASSIST blocked > {command}]` in `brightyellow`, command-only, no reason** — 03.1-CONTEXT.md leaves exact terminal wording open, locked here to the scope note's own example, colour chosen per the Color section's justified reuse, and deliberately kept to one line/no reason to match every other bracketed terminal notice's length discipline.
- **No new "autopilot remains ON" copy** — the absence of a notice is the signal; matches "no speed bumps" guidance and D-06's own framing that a block is not a state change.
- **Reviewer-failure kinds reuse three of the six existing D-13 notices verbatim, with no vendor/call-identity text added** — 03.1-CONTEXT.md (D-09) requires "the existing D-13 failure notice for that failure kind"; this phase maps each of the three reviewer-failure conditions (unreachable, rate-limited, unreadable) to its exact existing sibling notice rather than writing new strings.
- **`AIDecisionPayload.message` reused to carry the blocked reason on a `kind: 'decision'` payload**, rather than adding a new payload field — 03.1-CONTEXT.md explicitly leaves "the websocket event shape for a blocked decision" open and suggests exactly this extension ("extend the existing `ai` event with outcome `blocked` and a reason").

None of these affect what the owner sees in terms of information or interaction — only implementation-level styling, copy-wording, and data-shape choices, consistent with "no speed bumps" guidance. Every locked wording from D-02, D-06, D-07, D-08, D-09, and Phase 3's carried-forward D-13 strings is reproduced verbatim above; nothing here alters owner-visible state semantics.
