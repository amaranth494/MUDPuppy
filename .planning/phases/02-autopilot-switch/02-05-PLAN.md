Plan 02-07 runs this script against Railway staging and files its output as `evidence/03-canned-report.txt`. No criterion in this phase is established by a database query.
Output: an executable `scripts/verify-phase2.sh`, a fixture set that lets it prove itself with no server, and a negative fixture set proving it can fail.

Criterion labels used throughout the script and its report map one to one onto the ROADMAP Phase 2 success criteria:

| Label | ROADMAP Phase 2 criterion |
|-------|---------------------------|
| C1 | `#AUTO ON` engages only when the profile passes the Phase 1 gate; `#AUTO OFF` disengages; the indicator always matches the true server-held state, including after a page refresh |
| C2 | A game command typed by the human while engaged disengages autopilot before the command is sent; alias, trigger and timer commands do not trip the wheel-grab |
| C3 | A disconnect while engaged moves autopilot to waiting, nothing is issued, the connection returning resumes to on, and `#AUTO OFF` while waiting stays off after reconnecting |
| C4 | The owner can create a profile, accept the policy, and hand-play with the AI disengaged; nothing about ordinary play changes |

What this harness can and cannot reach, stated in the script's own header so the report is self-describing: C2 and C3 are websocket and live-MUD behaviours — engaging autopilot at all requires a connected game (D-03), which this script does not and must not fabricate. They are printed as SKIP lines naming their screenshot and log evidence, never as PASS. C1 and C4 are reachable in the states this script can create: gate refusal before acceptance, the no-connected-game refusal after acceptance, the already-off no-op, the status answer, the ownership check, input validation, and the agreement between the two endpoints.

Endpoints, all under `${BASE_URL}/api/v1`:
- POST `session/autopilot` — body `{action, connection_id}`, response `{state, outcome, gate_allowed, gate_message, policy_version}` (plan 02-02)
- GET `session/status` — response now carries `autopilot_state` (plan 02-02)
- POST `profiles/{connection_id}/policy/accept` — Phase 1, unchanged, used to move the fixture profile from unaccepted to accepted mid-run

Exact strings the report must assert character for character:
- Refusal: `AI Player has not been configured for this connection. Accept the Safety and Abuse policy in AI Player settings before engaging autopilot.`
- Policy version: `1.0`
- Outcome vocabulary: `engaged`, `disengaged`, `already-on`, `already-off`, `refused-gate`, `refused-no-session`, `status`

Authentication note carried over from Phase 1: this server's login issues an emailed one-time code, so the script never logs in. The caller supplies an existing session cookie.

    Copy `scripts/verify-phase1.sh`'s structure wholesale: the same flag parsing (`--self-test`, `--self-test-negative`, `--no-tests`, report path as the last positional, usage and exit 2 with no argument), the same `exec > >(tee "$REPORT") 2>&1` opening, the same header block printing a UTC timestamp, `BASE_URL`, `CONNECTION_ID` and `git rev-parse --short HEAD`, the same `_get_field` helper with its `command -v jq` guard and grep fallback, the same `_http` helper shape, and the same `_check` helper incrementing a failure counter.     Run the steps in exactly this order, each printing a banner with the method and path, the HTTP status, the raw response body, then its verdict lines:
    1. GET `session/status` — `_check C1` that `autopilot_state` is `off` on a fresh session. Record it.
    2. POST `session/autopilot` `{"action":"status","connection_id":$CONNECTION_ID}` — `_check C1` that `state` is `off`; `_check C4` that `gate_allowed` is `false` and `gate_message` equals the refusal sentence character for character.
    3. POST `session/autopilot` `{"action":"on","connection_id":$CONNECTION_ID}` — `_check C1` that `outcome` is `refused-gate`, `state` is `off` and `gate_message` equals the refusal sentence. This is `#AUTO ON` refused before acceptance.
    4. GET `session/status` — `_check C1` that `autopilot_state` is still `off`: the refusal changed nothing.
    5. POST `profiles/${CONNECTION_ID}/policy/accept` — `_check C4` that `accepted` is `true` and `accepted_version` is `1.0`. This is the Phase 1 endpoint, used here only to move the fixture profile into the accepted state.
    6. POST `session/autopilot` `{"action":"on","connection_id":$CONNECTION_ID}` — `_check C1` that `outcome` is now `refused-no-session` and `state` is `off`. The gate passes and the switch still refuses, because there is no connected game (D-03); the reason for refusal changed and the position did not.
    7. POST `session/autopilot` `{"action":"status","connection_id":$CONNECTION_ID}` — `_check C1` that `gate_allowed` is `true`, `policy_version` is `1.0` and `state` is `off`. These are the two halves of the `#AUTO STATUS` line the owner sees.
    8. POST `session/autopilot` `{"action":"off","connection_id":$CONNECTION_ID}` — `_check C1` that `outcome` is `already-off` and `state` is `off` (D-04).
    9. POST `session/autopilot` `{"action":"on","connection_id":$NOT_OWNED_CONNECTION_ID}` — `_check C4` that `outcome` is `refused-gate` and `gate_allowed` is `false`: a connection the caller does not own is refused by the ownership-scoped lookup, not engaged.
    10. POST `session/autopilot` `{"action":"sideways","connection_id":$CONNECTION_ID}` — `_check C1` that the HTTP status is `400`.
    11. GET `session/status` — `_check C1` that `state` is present and `autopilot_state` is `off`, matching step 8's answer: the badge's source of truth and the switch endpoint agree, which is the refresh-correctness claim.
    12. `_skip C2` naming `evidence/07-wheel-grab.png`, `evidence/08-trigger-keeps-on.png` and the `[AI-PLAYER] autopilot ... cause=wheel-grab` lines in `evidence/04-staging-ai-player.log` as the proof instead.
    13. `_skip C3` naming `evidence/09-waiting-after-drop.png`, `evidence/10-resume-after-reconnect.png`, `evidence/11-off-while-waiting-stays-off.png` and the `cause=disconnect` and `cause=resume` lines in `evidence/04-staging-ai-player.log`.

    Finish with a summary block: one line per criterion reading `PASS` only when every check carrying that label passed, `SKIP` when the criterion has no checks and only skips, and `FAIL` when any check with that label failed; then `TOTAL CHECKS: n  FAILURES: m  SKIPPED: k`. Exit 0 when the failure counter is zero and 1 otherwise, so the script is a gate as well as a report.

    Print no secret: never echo `SESSION_COOKIE`. The responses this script prints carry no game text and no profile prose, so they are printed whole.
