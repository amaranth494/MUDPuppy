<objective>
Make the play screen tell the truth about the switch. A badge sits beside the connection badge reading On, Waiting or Off, filled from the server's own status response so a hard refresh re-syncs it rather than guessing. Every state change the owner did not personally type produces the exact bracketed line the approved UI contract specifies: taking the wheel, parking on a drop, resuming on return. And with autopilot off, nothing changes at all — no new line, no banner, just a badge reading Off.

Purpose: this plan closes the owner-visible half of all four ROADMAP criteria and is where D-12 is either honoured or broken. It also completes the wheel-grab by labelling the one submission path that bypasses the automation engine, which is how a blank Enter takes the wheel (RESEARCH Pitfall 2).
Output: a new badge component, three small extensions to the session context, the badge's CSS and placement, and the notice and source wiring in the play screen.
</objective>

| Transition | Who prints it | Line and colour |
|---|---|---|
| The owner typed `#AUTO ON`/`OFF`/`STATUS` | the `case 'AUTO':` branch from plan 02-04, off the HTTP response's `outcome` | the outcome table in 02-04 |
| Wheel-grab (this tab typed a game command) | the `onAutopilot` websocket handler in `PlayScreen.tsx`, keyed on cause `wheel-grab` | `[Autopilot disengaged: you took the wheel]`, white |
| On becomes Waiting (the connection dropped) | the autopilot-transition effect in `PlayScreen.tsx` | `[Autopilot waiting for reconnect]`, brightyellow, on the line after the existing `[Disconnected]` |
| Waiting becomes On (the connection returned) | the same effect | `[Reconnected]`, white, then `[Autopilot resuming]`, brightgreen — two lines, not concatenated |

The transition effect fires only for on-to-waiting and waiting-to-on.
