# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope actually covered here** (per orchestrator instruction — nothing else is in Phase 2 UI):
(a) the autopilot header badge beside the existing connection badge — ON / WAITING / OFF, colours, placement, size, exact label text, state → visual mapping;
(b) the bracketed terminal notice lines for every state change (D-11), verbatim copy, styled like the existing `[Disconnected]` line, always through the local-echo path, never sent to the game;
(c) the one-line `#AUTO` / `#AUTO STATUS` output format (D-05);
(d) the D-12 invariant: autopilot OFF looks exactly like ordinary play today.

No settings panels, no modals, no new pages. All tokens below are carried over unchanged from `01-UI-SPEC.md`; nothing new is introduced except two new CSS class blocks (badge variants) and the copy strings this phase requires.

Existing tokens in `index.css`, reused as-is, unchanged from Phase 1:

|------|------|--------|-------------|

| Body | 16px (`--font-size-base`) | 400 (regular) | 1.5 |

Usage in this phase:

## Color

Existing tokens in `index.css`, reused as-is — this is already a compliant 60/30/10 system, unchanged from Phase 1:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0a0a0a` (`--color-bg`) | Page background (unaffected by this phase) |
| Secondary (30%) | `#111111` (`--color-bg-secondary`) | Header background (unaffected by this phase) |
| Accent (10%) | `#00ff00` (`--color-text` / `--color-success`, same hex) | Reserved for: the autopilot badge's **ON** state (dot + text colour + background tint), exactly mirroring `.session-badge.status-connected`'s existing use of `var(--color-success)` |
| Secondary state | `#ffff00` (`--color-warning`) | Reserved for: the autopilot badge's **WAITING** state, exactly mirroring `.session-badge.status-connecting`'s existing use of `var(--color-warning)` |
| Neutral | `#888888` (existing hardcoded value already used by `.session-badge.status-disconnected`, not a token but an established precedent) | Reserved for: the autopilot badge's **OFF** state, exactly mirroring `.session-badge.status-disconnected` |
| Destructive | `#ff4444` (`--color-error`) | Reserved for: the engage-gate refusal notice and the no-connection refusal notice (terminal text only; no new UI element uses this) |

Accent reserved for: the autopilot badge's ON state only (dot, label colour, background tint) and the `[Autopilot engaged]` / `[Autopilot resuming]` terminal notices (ANSI `brightgreen`, the terminal-text equivalent of the same accent). Never used for body text, labels, or any element unrelated to "autopilot is actively ON."

No new hex values are introduced by this phase — the OFF state's `#888888` and its `rgba(128,128,128,0.2)` background tint already exist verbatim in `index.css` for `.session-badge.status-disconnected` and are reused unchanged, not reinvented.

| Notice | Colour name | Rationale |
|---|---|---|
| `[Autopilot engaged]` | `brightgreen` | Matches badge ON accent |
| `[Autopilot disengaged]` | `white` | Neutral, matches existing `[Disconnected]` precedent |
| `[Autopilot disengaged: you took the wheel]` | `white` | Same neutral family as any owner-initiated disengage |
| `[Autopilot is already on]` | `white` | Informational no-op, not an error |
| `[Autopilot is already off]` | `white` | Informational no-op, not an error |
| Engage-gate refusal (Phase 1's exact `EngageGateRefusalMessage` string) | `red` | Matches the existing `[ERROR]` precedent (`{ color: 'red' }` in `PlayScreen.tsx`) |
| `[Autopilot needs a connected game; connect first]` | `red` | Same refusal family as the engage-gate refusal |
| `[Disconnected]` | `white` | Unchanged, existing line |
| `[Autopilot waiting for reconnect]` | `brightyellow` | Matches badge WAITING accent |
| `[Reconnected]` | `white` | Neutral, symmetric counterpart to `[Disconnected]` |
| `[Autopilot resuming]` | `brightgreen` | Matches badge ON accent — resuming lands on ON |
| `#AUTO` / `#AUTO STATUS` output line | `brightyellow` | Matches the existing `#HELP` precedent (`brightYellow` in `evaluator.ts`'s `case 'HELP':`) for informational, on-demand output |

## Copywriting Contract

Plain, non-marketing, terminal-friendly — matches the existing voice used throughout the app and Phase 1's contract.

| Element | Copy |
|---------|------|
| Autopilot badge label, ON | `Autopilot: On` (rendered uppercase by CSS `text-transform: uppercase`, exactly like `.session-badge`) |
| Autopilot badge label, WAITING | `Autopilot: Waiting` |
| Autopilot badge label, OFF | `Autopilot: Off` |
| Engage notice | `[Autopilot engaged]` (verbatim, owner-locked D-11) |
| Disengage notice (`#AUTO OFF`) | `[Autopilot disengaged]` (verbatim, owner-locked D-11) |
| Wheel-grab notice | `[Autopilot disengaged: you took the wheel]` (verbatim, owner-locked D-11) |
| Already-on no-op | `[Autopilot is already on]` (verbatim, owner-locked D-04/D-11) |
| Already-off no-op | `[Autopilot is already off]` (verbatim, owner-locked D-04/D-11) |
| No-connection refusal | `[Autopilot needs a connected game; connect first]` (verbatim, owner-locked D-03/D-11) |
| Engage-gate refusal | `[` + the exact Phase 1 `EngageGateRefusalMessage` string (currently: `AI Player has not been configured for this connection. Accept the Safety and Abuse policy in AI Player settings before engaging autopilot.`) + `]` — bracket-wrapped for visual consistency with every other state-change notice in this list (see Claude's Discretion below); the sentence itself is unchanged from Phase 1's contract, this phase does not restate or paraphrase it |
| Disconnect-while-engaged sequence | `[Disconnected]` then, on the next line, `[Autopilot waiting for reconnect]` (verbatim, owner-locked D-11) — two separate lines, not concatenated |
| Reconnect-while-waiting sequence | `[Reconnected]` then, on the next line, `[Autopilot resuming]` (verbatim, owner-locked D-11) — two separate lines, not concatenated |
| `#AUTO` / `#AUTO STATUS` output | `Autopilot: {STATE}. Engage gate: {gate result}.` — one line, not bracket-wrapped (a status query response, not a state-change notice). `{STATE}` is exactly `ON`, `WAITING`, or `OFF`. `{gate result}` is either `passed (policy v{version} accepted)` when the gate allows, or the exact Phase 1 `EngageGateRefusalMessage` string when it refuses (not bracket-wrapped here — the surrounding sentence already establishes context). Examples: `Autopilot: OFF. Engage gate: passed (policy v1.0 accepted).` and `Autopilot: OFF. Engage gate: AI Player has not been configured for this connection. Accept the Safety and Abuse policy in AI Player settings before engaging autopilot.` |
| Empty state (ordinary play, autopilot OFF) | No new copy exists — D-12: the badge reads `Autopilot: Off` and nothing else changes. No banner, no extra terminal line, no first-run tooltip. |
| Error state | Not applicable beyond the refusal notices above — this phase has no AI intelligence and no failure modes beyond "gate refused" and "no connection," both already covered. |
| Destructive confirmation | None. `#AUTO OFF` is not destructive (it is always reversible by `#AUTO ON`) and requires no confirmation step, per D-01/D-04 — it is a plain toggle, not a delete action. |

## Layout & Component Reuse (phase-specific — extends the template because this phase introduces new screen content)

All markup reuses existing CSS structure from `frontend/src/index.css`; two new class blocks are added, both direct siblings of `.session-badge*`.

**New component:** `frontend/src/components/AutopilotBadge.tsx` — same shape as `SessionBadge.tsx` (a small function component reading state from context, no props, a coloured dot + label, a `title` tooltip). It reads autopilot state from `useSession()` (or an equivalent context field added by this phase per RESEARCH.md's `SessionContext.tsx` extension), not from local component state.

**Placement:** `frontend/src/components/Header.tsx`, inside `.header-right`, immediately after the existing `<SessionBadge />` and before the account menu:
```tsx
<div className="header-right">
  <SessionBadge />
  <AutopilotBadge />
  <div className="account-menu">...
```
This satisfies D-10 ("a header badge beside the existing connection badge") with the connection badge reading first (is the connection itself even up) and the autopilot badge reading second (what the AI is doing given that connection) — the natural information order.

**New CSS** (append to `index.css`, directly below the existing `.session-badge.status-error` block, same file, same pattern):
```css
.autopilot-badge {
  display: flex;
  align-items: center;
  gap: var(--spacing-sm);
  padding: var(--spacing-xs) var(--spacing-md);
  border-radius: 999px;
  font-size: var(--font-size-sm);
  font-weight: bold;
  text-transform: uppercase;
}

.autopilot-badge-dot {
  width: 8px;
  height: 8px;
  border-radius: 50%;
  background: currentColor;
}

.autopilot-badge.state-on {
  background: rgba(0, 255, 0, 0.2);
  color: var(--color-success);
}

.autopilot-badge.state-waiting {
  background: rgba(255, 255, 0, 0.2);
  color: var(--color-warning);
}

.autopilot-badge.state-off {
  background: rgba(128, 128, 128, 0.2);
  color: #888;
}
```
This is a verbatim structural copy of `.session-badge`/`.session-badge-dot`/`.session-badge.status-*` (lines 137–206), renamed for the autopilot concept and reduced from four states to three (no "connecting"/"error" equivalent — autopilot has exactly ON/WAITING/OFF per D-01). No new spacing or colour values — every value above already exists in the file for the connection badge.

**Badge markup (inside `AutopilotBadge.tsx`):**
```tsx
<div className={`autopilot-badge state-${stateClass}`} title={`Autopilot: ${label}`}>
  <span className="autopilot-badge-dot" />
  <span className="autopilot-badge-text">Autopilot: {label}</span>
</div>
```
where `stateClass` is `on` | `waiting` | `off` and `label` is `On` | `Waiting` | `Off`, driven strictly by the server-held state (D-10) — the component never infers a state locally.

**Terminal notices:** no new component. Every bracketed line in the Copywriting Contract above is written through `automationEngine.echoLocal(message, { color })`, the exact mechanism already producing `[Disconnected]` and `[ERROR]` (`PlayScreen.tsx` lines 302–317). This guarantees, for free, D-11's requirement that these lines never reach the MUD. Whichever code path first learns of a transition (the `#AUTO` HTTP/websocket response for the acting tab, or the `onAutopilot`/`onDisconnect`/`onConnect` handlers for a passive tab) calls `echoLocal` with the exact string and colour from the tables above — this is plumbing, not a UI decision, and is left to the planner/executor per RESEARCH.md's architecture.

**`#AUTO` / `#AUTO STATUS` output:** rendered the same way `#HELP` renders its output today (`evaluator.ts`, `case 'HELP':` — `context.outputMessage?.(...)` with `brightYellow`/`reset` ANSI wrapping), not via `echoLocal`/`#ECHO`, since it is a direct command output rather than a re-dispatched local echo — this matches the existing `HELP` precedent exactly (Pattern 1 in RESEARCH.md) and keeps `#AUTO`'s own `case 'AUTO':` branch structurally identical to `case 'HELP':`.

## D-12 Invariant (explicit, non-negotiable)

With autopilot OFF:
- The autopilot badge reads `Autopilot: Off` in the OFF colour (`#888` / `rgba(128,128,128,0.2)`) — the only visible difference from today's play screen.
- No bracketed notice line of any kind appears. Ordinary connect, disconnect, typing, and command echo behave exactly as they do today, including the existing `[Disconnected]`/`[ERROR]` lines, unchanged in wording and colour.
- No new banner, tooltip, onboarding hint, or modal is shown anywhere in the play screen.
- This must hold from the moment a fresh profile is created and the policy accepted (Phase 2 success criterion 4) — there is no "first-time autopilot" empty state to design; OFF has no special first-run treatment.

## Claude's Discretion (visual contract only — does not change owner-visible behavior)

- **Badge label wording** (`Autopilot: On/Waiting/Off` vs. bare `On/Waiting/Off`): the prefix is added because two adjacent single-word pill badges (`Connected` next to a bare `On`) would be ambiguous about what "On" refers to; D-10 only specifies the state words themselves, not whether they're prefixed. Resolved in favour of the prefixed form.
- **Bracket-wrapping the engage-gate refusal message**: D-11 lists the refusal under "every state change also prints one short bracketed line," but the message itself is a full sentence, not a short tag. Resolved in favour of wrapping it in a single `[...]` pair for visual consistency with every other notice in the same list, without altering the sentence's wording (which is Phase 1's locked contract).
- **`#AUTO`/`#AUTO STATUS` NOT bracket-wrapped**: distinguished from the state-change notices because it is a query response the owner explicitly asked for, not a notification — mirrors `#HELP`'s existing unbracketed output style.
- **Exact CSS class names** (`.autopilot-badge` vs. reusing `.session-badge` with a second modifier namespace): a new sibling class was chosen over overloading `.session-badge.status-*` because the state vocabulary is different (on/waiting/off vs. connected/connecting/disconnected/error) and conflating them risks a future connection-state change silently reskinning the autopilot badge or vice versa.
- **Badge placement order** (autopilot badge after, not before, the connection badge): connection is the precondition for autopilot (D-03: no engage without a connection), so it reads first, left-to-right.
- **`title` tooltip content on the badge**: informational only (`Autopilot: {label}`, matching the visible text); no owner-visible behavior depends on it.
- **ANSI colour names chosen for each notice** (e.g., `brightgreen` vs. plain `green`): chosen to match the terminal's existing bright-colour precedents (`#HELP`'s `brightYellow`, the automation-echo `brightcyan`) rather than the dimmer standard-8 palette, for legibility against the near-black terminal background.

None of these affect what the owner sees in terms of information or interaction — only implementation-level styling and copy-formatting choices, consistent with "no speed bumps" guidance. Every locked wording from D-04/D-05/D-11 is reproduced verbatim above; nothing here alters owner-visible state semantics.
