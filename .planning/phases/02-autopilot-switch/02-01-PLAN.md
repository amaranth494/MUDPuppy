<objective>
Give autopilot a position that the server owns and that a dropped connection cannot flip. This plan builds the three-value state machine (on, off, waiting), hangs it off `Manager` as a fourth user-keyed map that lives independently of the session map, and hooks the two lifecycle choke points so a disconnect parks an engaged autopilot and the next successful connect resumes it — with one `[AI-PLAYER]` line per call so the behaviour is readable in a staging log.

Purpose: this is the phase's central correctness risk. RESEARCH Pitfall 1 shows that `Manager.Disconnect` deletes the user's `*Session` from its map on every disconnect reason, and `GetSession` fabricates a zero-value replacement — so autopilot state stored on `Session` would be destroyed at the exact moment WAITING has to exist. Everything else in Phase 2 (the HTTP switch, the wheel-grab, the badge) reads this state; it is decided here, once, and proved by `go test` before any of them are built.
Output: `internal/session/autopilot.go` and its table tests, an extended `internal/session/manager.go`, and `internal/session/manager_test.go` — the first test file this package has ever had, and the one that exercises `Disconnect` end to end under `-race`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Websocket/REST goroutines → `Manager` maps | Several goroutines read and write the new autopilot map concurrently with `Connect`/`Disconnect` |
| Go process → server log | Deploy logs are readable by anyone with staging log access; whatever is logged is disclosed |
| Session lifecycle → autopilot lifecycle | The session map is deleted on every disconnect; autopilot state must not share that lifetime |
