<objective>
Make the owner's words change what AI-player does next. Plan 05-05 gave the owner a conversation; this plan gives that conversation its one power: a line the owner asks for becomes a standing suggestion AI-player reads on every decision for the rest of the login, and a line the owner takes back in words disappears from the next one.

Purpose: this is success criterion 1 — a chat message sent while the AI plays is reflected in its next decision, verifiable from the logged reasoning. It is also where this phase's own new risk lives: AI-chatter reads untrusted game text and model-written memory and then writes lines AI-player reads as guidance from the owner. The answer is two-layered and both layers are built here — the coaching store has exactly one writer, `HandleChat`, driven only by an inbound owner message, and coaching is still mechanically delimited and neutralised in both prompts so nothing inside it can forge a marker or outrank a conduct rule.

This plan also closes the one thing D-17 named that plan 05-05 could not yet supply: **AI-chatter reads the coaching currently in effect.** Without it the chat model is asked to withdraw lines it has never seen — and because the chat call is a stateless single shot, "forget what I said about the north road" would be answered by a model guessing at wording it cannot know, so the withdraw would silently match nothing against a real model even while a fake-model test passed.

Output: the coaching store with Session Memory's exact lifetime, push and withdraw on the chat answer, the coaching in effect inside AI-chatter's own prompt, the reply that quotes the exact line sent, the thinking-stream marker, the coaching block in both of AI-player's prompts, the GET reads the panel reloads from, and the red-team corpus items that attack through this new channel.
</objective>

Claude's Discretion settled by the planner for this plan:
- Coaching is stored in the `game_sessions.coaching_suggestions` JSONB column migration 015 already added, read and written with the same three-method shape Session Memory uses, and inherited across the login boundary by the same `login_started_at`-bounded query.
- Ceilings, enforced in Go on both the way in and the way out: at most **8** standing suggestions (`maxCoachingBullets = 8`), each truncated to the existing `maxBulletChars` of 200 and neutralised by the existing `neutraliseLine`. A push that would exceed the count drops the oldest suggestion and says so in the reply.
- The reply's quoting convention is composed by the **server**, not by the model: for each line actually written to the store, `HandleChat` prefixes the reply with `Sent to AI-player: {line}` and, for each line actually removed, `Withdrew from AI-player: {line}`, using the stored text verbatim. A model that claims to have pushed something it did not cannot produce that prefix, so what the owner reads is always what AI-player will read.
- **AI-chatter sees the coaching in effect.** D-17 names it among the things AI-chatter reads, and a withdraw cannot work without it: the chat call is stateless, so the model has no memory of lines it pushed on earlier turns. The current list travels in the chat prompt in its own `<COACHING>` block, delimited and neutralised like every other block, and the instruction tells the model to copy a line **verbatim from that block** into its `withdraw` array rather than paraphrasing it. Exact-text matching then succeeds against a real model, not just against a fake one.
- Withdraw matching is exact-text first, then case-insensitive whole-string match; a withdraw that matches nothing produces a plain reply saying nothing matched, and removes nothing.
- The `[Coaching received]` marker is emitted by `HandleChat` at the moment of a push or withdraw, as a `Kind: "system"` Event with `Outcome: "coaching-received"` on the existing decision channel, carrying no suggestion text (owner-confirmed).
- **Bracket convention (verified in code; the same one plan 05-01 and plan 05-05 record).** `frontend/src/components/AIAssistPanel.tsx` wraps a system-kind AI event's message in square brackets when it renders it. So the marker's `Message` on the wire is the **unbracketed** text `Coaching received`, and the owner reads the locked string `[Coaching received]`. Writing the brackets server-side would render `[[Coaching received]]` and fail the locked copy. The acceptance criteria grep for the unbracketed form deliberately.
- The new read endpoints are `GET /api/v1/profiles/{connection_id}/ai-coaching` and `GET /api/v1/profiles/{connection_id}/ai-conversation`, GET-only, following the `ai-memory` sub-resource exactly. There is no PUT for either (D-18, D-19).
