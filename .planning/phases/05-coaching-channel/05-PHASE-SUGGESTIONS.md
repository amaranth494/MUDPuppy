# Phase 5: end-of-phase suggestions

This is not a security report. It does not carry any risk decision and it does not affect whether Phase 5 closes. It exists because the owner's own rule at the Phase 5 security review was: "These are not security risks.  Don't treat this as a backlog review.  If you have end of Phase suggestions, that need a place in upcoming Phases, then make a separate report." This is that report — a plain list of things noticed during Phase 5 that are not safety problems, each with where it might fit next.

| # | What it is | Why it matters | Where I suggest it goes |
|---|-----------|-----------------|---------------------------|
| a | During the walkthrough, a standing coaching suggestion ("always look at the room before moving to a new room") made AI-player issue `look` several times in a row at one spot before moving on. Nothing was blocked and nothing harmful was sent — it just wasted turns and AI calls until the owner took the suggestion back in words. | A repeating command is a real cost the owner can only see after it has already happened. A future version of AI-player could notice its own command repeating and say so in the stream, rather than the owner having to catch it live. | With the owner's planned advanced AI-player logic work. |
| b | On 2026-09-18 the owner said: "I want to make adjustments to how models are used in later Phases." During this phase the free daily quota for `gemini-3.5-flash-lite` blocked testing for most of a day, and the server only knows how to talk to one provider (Gemini), so an OpenAI key the owner offered from another Railway project could not be used. AI-player, AI-chatter, and the safety checker could each have their own model setting instead of sharing one. | Model choice affects cost, availability, and — as the Phase 5 security review found — how reliably the safety checker catches an attack. This is a design question, not a small fix. | Suggest this gets its own discussion before Phase 6 planning, separate from Phase 6's own scope. |
| c | AI-chatter's conversation memory is scoped to one game session, so it forgets the conversation every time the game reconnects, even though the panel still shows the old lines on screen. | The owner sees a conversation that looks continuous but the AI genuinely does not remember it after a reconnect. This is a memory-and-continuity gap. | Fits Phase 6 (Measurement and Memory). |
| d | The play screen (`frontend/`) has no automated test runner at all — this phase's own layout fixes are proven only by a type-check, a build, and screenshots. Adding one means adding an npm dependency, which this phase's own rules left as the owner's call, not something to decide unilaterally. | Without an automated test runner, a future change to the play screen could silently break these fixes and nothing would catch it before a human looked. | A small standalone fix — needs the owner's decision on adding the dependency. |
| e | The Help page runs numbered steps together in one paragraph, in every article, not just this phase's new one. This is a limit in how the Help page renders its content, older than Phase 5. | Numbered instructions that don't actually render as separate steps are harder to follow, everywhere in the Help section. | A small standalone fix. |
| f | A hard page refresh drops the live game view and needs a reconnect. This is pre-existing behaviour, older than Phase 5, and was seen again during this phase's walkthrough. | Every hard refresh interrupts play, even though the reconnect does recover the session correctly. | A small standalone fix. |
| g | The staging harness's C1 check (pause and resume) was SKIP in both of this phase's staging runs, because autopilot was off each time the harness ran and it never turns it on itself by design. | Pause and resume were proven live by the owner's own walkthrough and a screenshot, not by the harness. The harness itself has never actually exercised this check on staging. | Run the harness once with autopilot on at the next staging session, as an operational step rather than a code change. |
| h | Live model tests should run one at a time, spaced out. The `-run TestLiveCorpus` pattern used to select one live test actually starts both live tests, and having three live runs share the free-tier key at once caused 10 to 11 of 40 samples to fail with no answer from the model, not a real measurement. | This cost real time and quota during Phase 5's own review, and would recur in any future phase that runs live model tests without noticing the pattern match. | A small standalone fix (a more specific test filter, or a documented rule to run live tests one at a time). |
| i | Two small code tidy-ups noted in this phase's own code review that are not security matters: a comment claiming two conversation writes "never collide," which is not actually true at the database's read-committed isolation level (IN-02); and an extra status request made on every 15-second poll that runs a database lookup the poll doesn't otherwise need (IN-07). | Neither affects correctness or safety today, but both are small, known pieces of debt worth cleaning up together. | A small standalone fix. |
| j | Two developer-machine papercuts found while working on this phase: a fresh git worktree starts on a stale commit rather than the branch's current HEAD, and one migration test fails on a Windows checkout because git converts the file's line endings. Neither is a defect in the shipped product. | These slow down whoever sets up a new working copy of this repository, on this platform. | A small standalone fix, for the project's own developer tooling. |
| k | Two things are still sitting on staging from earlier phases: the throwaway "Hand Play (no policy)" connection profile, and a game profile still showing the Phase 4 goal box's placeholder text ("No session goal set") because no goal has been set there. Neither is a security exposure — both were already covered by this phase's own regression checks. | Staging accumulates test fixtures and empty state across phases; a periodic tidy-up keeps it closer to what a real profile looks like. | A small standalone fix (or folded into the next staging clean-up pass). |

The owner also has play-feature ideas of his own to add; this report does not include them.
