<objective>
Give the AI a working memory it curates itself, and let the owner watch it do it.

The memory model is explicit that this layer is not a transcript: it is a compact, continually curated set of facts — added when something consequential happens, updated when circumstances change, merged when two entries describe the same situation, removed when they stop mattering. The simplest mechanism that does all four is to let the model rewrite the whole short list whenever it wants to change anything, as two extra fields on the answer it already returns. No extra model call, so the call cap is unaffected; no entry ids to track; "remove" is just absence from the next list.

Quest Memory works the same way but with a different lifetime: bullets germane to the goal go to the active Quest and persist across sessions, which is the whole point of the Quest layer. Session Memory lives for the game connection and is stored with the game session so Phase 6 can consolidate it.

Purpose: D-10 and D-11, the second and third layers of `.specify/specs/ai-memory-model-v1.md`, and REQ-doc-continuous-visible-play's promise that the owner sees what the AI is doing — which now includes what it has decided to remember.
Output: the two answer fields and their schema, the curation and persistence in the driver, a read-only endpoint, and the collapsible panel section.

Editing memory by hand is Phase 5. Quest Memory is not shown on the panel this phase (D-11); the owner recalls it through the chat pane once Phase 5 builds one. Nothing here closes a Quest.
</objective>

Claude's Discretion recorded for this plan (settled by the planner):
- Schema shape: two flat arrays of strings, `session_memory` and `quest_memory`, rewritten in full by the model whenever it wants to change anything — chosen over an add/update/remove operation list, which is strictly more machinery for the same capability and invites a class of entry-id bugs (04-RESEARCH Assumption A3, Don't Hand-Roll). Both fields are optional: absent means leave memory alone, present means replace.
- Ceilings, already applied on the way in by plan 04-07 and now also on the way out: 30 Session Memory bullets and 20 Quest bullets, each truncated to 200 characters, enforced in Go regardless of what the schema requests (Assumption A7).
- Storage: Session Memory is a JSONB array on the existing `game_sessions` row (its lifetime already matches D-10's "lives for the game connection ... stored with the game session"); Quest Memory is the `bullets` column on the active Quest. Both columns exist as of migration 013.
- No system line is printed when memory changes (04-UI-SPEC: a line on nearly every decision would drown the panel); the live-updating section with its count is the visible signal.
- The panel section defaults to collapsed and its open/closed state is component-only.

The model's own memory text is untrusted data: plan 04-07 already delimits it in both prompts, and nothing in this plan may treat a memory bullet as an instruction or interpolate one into a log line.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Model-written memory → the database | The model decides what is written; the server decides how much and whether it is treated as data |
| Stored memory → every future prompt | A poisoned bullet re-enters every later decision for the life of the connection or the Quest |
| The memory endpoint → the browser | A read endpoint over another owner's connection would disclose their play |
| Memory content → logs and evidence | Bullets are written from game text and may contain anything |

## STRIDE Threat Register

| Threat ID | Category | Severity | Component | Disposition | Mitigation |
|-----------|----------|----------|-----------|-------------|------------|
| T-4-03 | Tampering / Elevation of Privilege | High | memory poisoning: a bullet written under the influence of hostile game text returning as standing context on every later decision | mitigate (partial) + defer to security review | Plan 04-07 delimits both memory blocks as untrusted in both prompts; this plan bounds how much can be written and keeps it visible to the owner; the residual — a poisoned bullet that reads as a plain fact rather than an instruction — is this phase's new active risk and goes to the Phase 4 security review with three dispositions and nothing pre-chosen |
| T-4-10 | Denial of Service (unbounded growth) | Medium | a model returning hundreds of long bullets, inflating storage and every future prompt | mitigate | `truncateBullets` enforces 30/20 items at 200 characters in Go, independently of the schema (Assumption A7), proven by `TestMemoryCeilingsAreEnforced` |
| T-4-09 | Spoofing / broken access control (IDOR) | High | the memory endpoint serving another owner's session memory | mitigate | `getProfileByConnectionID` unchanged, re-proven by the harness's not-owned step (plan 04-10) |
| T-4-29 | Denial of Service (memory loss costs a command) | Low | a malformed memory field or a storage error dropping the decision itself | mitigate | The fields are optional and decode-tolerant; a store error is logged and the command still sends, proven by `TestDriverPersistsCuratedMemory`'s store-error case |
| T-4-05 | Information Disclosure | Medium | bullet text reaching an `[AI-PLAYER]` line, an evidence file or a screenshot's log pane | mitigate | The memory log line carries counts and lengths only; evidence screenshots are end-user browser frames, where the owner's own memory is already visible to him by design |
| T-4-SC | Tampering (supply chain) | Low | `go.mod`, `frontend/package.json` | accept | No package is added |
</threat_model>
