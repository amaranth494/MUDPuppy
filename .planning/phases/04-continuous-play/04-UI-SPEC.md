# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope actually covered here** (per orchestrator instruction — nothing else is in Phase 4 UI):
(a) the one-line **session goal text box** at the top of the AI Assist panel (D-01 to D-04): placement, label, placeholder, save behaviour, the "No session goal set" empty state, editable-while-playing, and the "Goal changed: ..." system-line family;
(b) the read-only collapsible **Session Memory** section (D-10): default state, header with a count, bullet rendering, empty state, live update, never editable this phase;
(c) the new **system-line notices** in the panel and terminal, locked verbatim, in the 03-UI-SPEC voice, with no vendor text interpolated: cap reached (D-14), transient failure with count (D-15), retrying after a 503 (D-16), blocked repeatedly (D-17), goal changed/cleared (D-03), no goal set (D-02), memory updated (decided: no line), paused/resumed while disconnected (D-19: no new copy);
(d) the **badge updating from the `ai` message** on any disengage (D-18): stated as an invariant, not a visual change;
(e) the **"delete captured text now"** per-profile action (D-21): where it lives, its label, confirmation copy, result line;
(f) where the **call count and consecutive-failure/block counts** appear;
(g) the regression invariant extended to Phase 4;
(h) every new copy string, locked verbatim, in the Copywriting Contract table below.

Not covered: Quest Memory display (hidden this phase, D-11), chat/coaching (Phase 5), the debrief (Phase 6).

This phase adds **zero new CSS custom properties**. It reuses Phase 3's `--color-success`, `--color-warning`, `--color-error`, `--color-text-dim`, `--color-ai-accent`, the existing spacing/typography scale, and Phase 3.1's `.delete-confirm`/`.btn-danger` pattern exactly as they stand. No component library, no shadcn — unchanged from Phases 1–3.1.

## Color

Existing tokens in `index.css`, reused as-is — **no new custom properties this phase**:

| Role | Value | Usage in this phase |
|------|-------|-----------|
| Accent (10%, AI identity) | `#ff66ff` (`--color-ai-accent`) | **Not used by anything new this phase.** The goal box, status line, and Session Memory bullets are owner-facing or curated-fact surfaces, not "the AI just issued a command" — using the AI-identity accent for them would blur that reservation. Unchanged reservation: sent AI commands only. |
| Warning | `#ffff00` (`--color-warning`) | **Extends its existing "still going, not yet resolved" reservation (established 03.1-UI-SPEC.md) to two new cases:** the sub-threshold transient-failure notice (D-15's "N of M", the loop is continuing, nothing has stopped) and the 503 retry-in-flight notice (D-16, a retry is happening right now). Unchanged: the WAITING system line, a single blocked decision. |
| Destructive | `#ff4444` (`--color-error`) | **Extends its existing "Autopilot disengaged due to something other than the owner's own action" reservation to three new cases:** the call-cap-reached notice (D-14), the blocked-repeatedly notice (D-17), and the new `icm-refused` kind's at-threshold failure notice (D-15). Unchanged: the six existing D-13 failure notices, the engage-gate and D-20 refusals. |
| Neutral | `#888888` (existing hardcoded precedent) | **Extends its existing "plain, non-alarming state fact" reservation to the goal-changed/goal-cleared system line** (D-03) — a goal edit is the owner's own action, informational, not a safety event, so it takes the same neutral treatment as the plain `[Autopilot disengaged]` line, never red or yellow. |
| Text-dim | `var(--color-text-dim)` | The goal box's `.form-hint`; the status line; Session Memory's bullets and empty state — all reuse the same dim body-text convention as every other hint/empty-state string in the app. |

### The governing rule (why nothing new is introduced)

Every locked notice in this phase falls into one of four buckets that Phases 3 and 3.1 already established colours for, so this phase extends three existing reservations rather than inventing a fourth or fifth:
1. **Red** = "Autopilot disengaged, and it wasn't the owner who did it" (cap reached, blocked-repeatedly, every D-13/D-15 at-threshold kind).
2. **Yellow** = "still trying, nothing has stopped yet" (waiting for reconnect, a single blocked decision, a sub-threshold failure count, a 503 retry in flight).
3. **Green** = "autopilot is actively on and working" (engaged, resuming) — untouched this phase.
4. **Neutral `#888`** = "a plain fact, not a safety event" (the owner took the wheel, the owner changed or cleared the goal).

Applying this rule consistently is itself the design decision this phase makes; no new token is justified because every new notice already has a home in one of the four buckets above.

**Save behaviour and the "No session goal set" state:** committing on blur (and on Enter, which blurs the input) rather than a separate button keeps the control as lightweight as the rest of the panel's "no input field... this phase" design (D-08's original framing for the panel, now the panel's first exception, deliberately kept minimal). The system line (`[Goal changed: {goal}]` / `[Goal cleared]`) that fires once the save succeeds **is** the save confirmation — no separate "Saved" indicator is introduced (see Claude's Discretion). When the goal is empty, the native `placeholder` text reads `No session goal set`, satisfying D-02 without a second, separately-styled empty-state element.

The goal box renders whenever the panel itself is mounted (policy accepted), independent of whether autopilot has ever been engaged — the owner can set a goal before the first `#AUTO ON` (D-01/D-02 do not require an active session).

```tsx
{autopilotState !== 'off' && (
```

### 6. Delete Captured Text Now (`frontend/src/components/AIPlayerPanel.tsx`, extended; D-21)

**Placement decision: the AI Player settings section, not the Logs section.** Reasoning: the captured text this action removes (decision snapshots and session transcripts, D-21) is a byproduct of AI play specifically, and the owner is already in this exact panel managing everything else AI-specific (conduct rules, approach guidance, the Never-Issue List). The Logs section (`SettingsPage.tsx` lines 1699–1717) is a read/browse surface — "Open Logging" opens a new tab to *view* history; placing a destructive delete action beside a "browse your history" button risks an accidental click while trying to view logs, and conflates viewing with destroying. Placed in `AIPlayerPanel.tsx`, it stays with the settings that already govern AI behaviour on this profile.

Positioned as its own block, visually separated from the non-destructive `.settings-actions`/"Save AI Settings" button (`AIPlayerPanel.tsx` lines 284–288) by a top border, so a click near "Save AI Settings" can never land on a destructive control:

```css
.ai-player-danger-zone {
  margin-top: var(--spacing-lg);
  padding-top: var(--spacing-md);
  border-top: 1px solid var(--color-border);
}
```

```tsx
<div className="ai-player-danger-zone">
  <p className="form-hint">
    This permanently deletes captured game-text snapshots and session transcripts for this
    profile. Decision rows, reasoning, and outcomes stay on record. This cannot be undone.
  </p>
  {confirmingDelete ? (
    <div className="delete-confirm">
      <span>Delete captured text now?</span>
      <button className="btn btn-sm btn-danger" onClick={handleDeleteCapturedText} disabled={isDeleting}>
        Yes
      </button>
      <button className="btn btn-sm" onClick={() => setConfirmingDelete(false)}>
        No
      </button>
    </div>
  ) : (
    <button className="btn btn-sm btn-secondary" onClick={() => setConfirmingDelete(true)}>
      Delete Captured Text Now
    </button>
  )}
</div>
```

`.delete-confirm` and `.btn-danger` are the exact classes a saved connection's delete action already uses (`ConnectionsHubModal.tsx` lines 339–355, `index.css` lines 1624–1632 and 1161–1168) — reused verbatim, not reinvented, because this is the same two-step "irreversible action, confirm inline" shape the app already has one precedent for. The confirm hint (stating exactly what is and isn't deleted) is shown unconditionally above the button — unlike the bare "Delete?" a connection row uses — because a saved connection's deletion is self-evident from context, while "captured text" is a new, unfamiliar concept this phase introduces and needs its scope stated in plain words (D-21's own retention distinction: decision rows survive, snapshots/transcripts do not).

Result: `Captured text deleted.` on success (`.message.message-success`, matching every other success message in this panel); `Failed to delete captured text — refresh the page to try again` on failure (`.message.message-error`, matching the existing "Failed to load X" pattern).

## Claude's Discretion (visual contract only — does not change owner-visible behavior)

- **Goal box saves on blur/Enter, no Save button** — D-01 to D-04 lock the field's existence, persistence, and editability, not its exact commit mechanism; a bare input matches the panel's existing "no extra chrome" discipline, and the resulting `[Goal changed: ...]`/`[Goal cleared]` system line doubles as the save confirmation, so no separate "Saved" indicator is introduced.
- **"No session goal set" rendered as the input's native placeholder, not a separate empty-state element** — the simplest reading of D-02 that satisfies "the panel shows..." without a second styled element competing for space in a 380px-wide panel.
- **Session Memory defaults to collapsed, component-only state (resets on remount)** — D-10 locks "collapsible... updates live," not a default open/closed state or persistence of the toggle itself; collapsed-by-default keeps the panel compact when a session first connects and Session Memory is empty (count 0), matching "no speed bumps."
- **Session Memory bullets render with no card/border, directly on the panel background** — matches the memory model's own framing of curated bullets as lightweight facts, not a boxed audit artifact (contrast with a decision card, which is a stored, audited event).
- **`▸`/`▾` disclosure glyphs** — chosen for thematic fit with the app's existing plain-Unicode-glyph convention (no icon library anywhere in the app); avoids introducing an SVG/icon-font dependency for a single toggle.
- **Status line is a persistent readout under the goal box, not folded only into notices** — CONTEXT.md explicitly leaves this open ("recommend a small muted status line... or only inside notices; pick one"); a standing readout was chosen because three independent mechanical limits (D-14, D-15, D-17) are being put under test this phase, and continuous visibility is cheaper than requiring the owner to infer proximity to a limit from transient text alone.
- **Status line hidden entirely while autopilot is `off`** — the counts reset to zero on every new stint (D-14) and are meaningless before an engage; hiding avoids a permanent "Calls: 0" line cluttering the idle panel.
- **`icm-refused` gets a new, phase-4-authored notice sentence** rather than reusing an existing D-13 kind's wording — 03-UI-SPEC.md's six notices never included this kind (it did not exist as a locked string in Phase 3); "the game's own limits refused the command" states the fact plainly without vendor/engine internals, matching the existing six sentences' voice and structure exactly.
- **Sub-threshold transient failures reuse the six-plus-one existing sentence fragments with a trailing `({N} of {M})` and drop "Autopilot disengaged"** rather than inventing wholly new sentences — this is the smallest change that satisfies D-15's "shows its notice with the count" while keeping one canonical sentence per failure kind, reused at both severities (below threshold: yellow, no disengage suffix; at threshold: red, existing suffix).
- **Colour assignment for the five new notice families (cap, blocked-repeatedly, transient, retrying, goal-changed/cleared)** — resolved by the four-bucket governing rule stated in the Color section, not by inventing new tokens; this is the primary color-related decision this phase makes.
- **`PlayScreen.tsx`'s `handleAI` 'system' branch changes from a hard-coded red to an outcome-keyed colour lookup** — required by the above; kept as a small `switch`/ternary rather than a lookup table to match the file's existing inline-conditional style at that call site.
- **Badge invariant framed as a data-flow contract, not a visual dimension** — D-18 has no owner-visible copy or styling implication; documenting it here (Section 5) exists so the checker does not mistakenly expect a new badge state or colour.
- **"Delete Captured Text Now" placed in the AI Player settings section, not Logs** — justified in Layout Section 6; the alternative (Logs section) was rejected because it conflates a destructive action with a browse/view action.
- **"Delete Captured Text Now" reuses the exact `.delete-confirm`/`.btn-danger` two-step pattern** already established for deleting a saved connection, rather than a new confirmation modal — the same "irreversible, confirm inline" shape, extended with an unconditional scope-stating hint since "captured text" is a new, unfamiliar concept (a saved connection's deletion needs no such explanation).
- **No system line for "memory updated"** — an update fires on or near every decision (D-10's add/update/merge/remove), so a line-per-update would dominate the panel; the collapsible section's own live-updating count and bullet list is the visible signal instead. This is the one place this phase deliberately chooses silence over a notice, consistent with "no speed bumps."
- **`AIDecisionPayload.outcome` extended with five new string literals** (`'cap'`, `'blocked-repeatedly'`, `'transient'`, `'retrying'`, `'goal'`) rather than a new payload shape — extends the existing union exactly as `03.1-UI-SPEC.md` extended it with `'blocked'`; exact backend field/enum naming remains executor discretion per that same precedent.

None of these affect what the owner sees in terms of information or interaction — only implementation-level styling, geometry, and copy-formatting choices, consistent with "no speed bumps" guidance. Every locked wording from D-01 to D-04, D-14 to D-17, D-19, D-21, and Phase 3/3.1's carried-forward strings is reproduced verbatim above; nothing here alters owner-visible state semantics.
