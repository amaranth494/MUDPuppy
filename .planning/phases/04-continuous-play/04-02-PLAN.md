<objective>
Close the two carry-forward defects that have nothing to do with the loop and everything to do with whether staging survives it. First: `ENCRYPTION_KEY_V1` is optional today, and when it is absent `crypto.DefaultKeyStore` silently generates a fresh random key at every process start — which is how every stored MUD password on staging became undecryptable after each redeploy during the Phase 3.1 walkthroughs, and how autopilot once found itself answering a character-creation prompt it was never meant to see. Second: migration `012`'s rollback re-adds a three-value CHECK constraint without first reconciling the `blocked` rows the phase it belongs to created, so a rollback fails partway once a single command has actually been blocked.

Purpose: D-25 (DR-3.1-04, criticality high) and D-26 (DR-3.1-05). Both were deferred at the Phase 3.1 review with the owner's instruction to remediate them here, and both are closed at this phase's security review through D-28. Neither depends on any other Phase 4 work, which is why they run in the first wave rather than waiting behind the loop.
Output: a startup gate with its test, a fixed rollback with a no-database test that proves the ordering, and the documentation and rotation procedure the owner asked for.

This plan changes no AI behaviour and touches no driver code.
</objective>
