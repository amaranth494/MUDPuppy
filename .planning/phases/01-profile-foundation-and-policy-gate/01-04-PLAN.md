Each observable state this plan creates has a named screenshot file in plan 01-05 — build the UI so those screenshots are unambiguous: one state on screen at a time, with the acceptance line, the hints and the field values all legible in a single viewport.

Endpoints delivered by plan 01-03 (all under `/api/v1`, session cookie via `credentials: 'include'`):
- GET `profiles/{connectionId}/ai-settings` and PUT the same path with `{conduct_rules, approach_guidance, ai_settings}`
- GET `profiles/{connectionId}/policy` returning `{text, version, accepted, accepted_at, accepted_version}`
- POST `profiles/{connectionId}/policy/accept` returning the same policy shape
- GET `profiles/{connectionId}/engage-gate` returning `{allowed, message}`

Error bodies are `{"error": "..."}` with HTTP 400 on every failure path; the existing `api.ts` convention reads `data.error` and ignores the status.

`accepted_at` arrives as an RFC3339 timestamp string (same shape as the existing `created_at`), so the UI-SPEC's `YYYY-MM-DD` display is its first 10 characters.

No frontend test framework exists and none is to be added in this phase. Automated verification for every task here is `npm run build` (which runs `tsc` first, so type errors fail the build).
