Purpose: the owner's evidence rule allows exactly two proof types, a canned report and a screenshot. This is the canned report. Plan 01-05 runs this script against Railway staging and files its output as `evidence/03-canned-report.txt`; no database query is used to prove anything.

Criterion labels used throughout the script and its report map one-to-one onto the ROADMAP Phase 1 success criteria:

| Label | ROADMAP criterion |
|-------|-------------------|
| C1 | A profile stores and returns conduct rules, approach guidance and AI settings, with blank model name / call cap / threshold preserved as blank and over-length input rejected |
| C2 | Values are readable and editable and survive; at the API level, an unrelated write does not disturb them |
| C3 | Policy is presented before acceptance and the engage gate refuses an unaccepted profile with the exact message, and allows an accepted one |
| C4 | Acceptance is recorded once with version 1.0 and a timestamp, is not forgeable through another endpoint, and does not change on repeat |

Endpoints (plan 01-03), all under `${BASE_URL}/api/v1`:
- GET/PUT `profiles/{connection_id}/ai-settings` — body `{conduct_rules, approach_guidance, ai_settings:{model_name, call_cap, disengage_threshold}}`
- GET `profiles/{connection_id}/policy` — `{text, version, accepted, accepted_at, accepted_version}`
- POST `profiles/{connection_id}/policy/accept` — same shape as GET policy
- GET `profiles/{connection_id}/engage-gate` — `{allowed, message}`
- GET/PUT `profiles/{connection_id}/timers` — pre-existing sub-resource, used to prove non-interference

Exact strings the report must assert character for character:
- Refusal: `AI Player has not been configured for this connection. Accept the Safety and Abuse policy in AI Player settings before engaging autopilot.`
- Over-length rejection: `Conduct rules must be 20000 characters or less`
- Policy version: `1.0`

Authentication note: this server's login issues an emailed OTP (`/api/v1/send-otp` then `/api/v1/login`), so the script never logs in. The caller supplies an existing session cookie; that keeps the harness usable against staging, which is where plan 01-05 runs it.

    Inputs: `BASE_URL`, `SESSION_COOKIE` and `CONNECTION_ID` read from the environment; the report file path is the last positional argument. Define `_check <label> <description> <condition-result>` printing `PASS <label>: <description>` or `FAIL <label>: <description>`, incrementing a failure counter on FAIL. Every step prints, in this order: a step banner with the method and path, the HTTP status, the raw response body, then its verdict line(s). The body is printed unconditionally, pass or fail — the owner reads bodies, not just verdicts.

    Run the steps in exactly this order:
    1. GET `profiles/${CONNECTION_ID}/policy` — `_check C3` that `accepted` is `false`, and `_check C4` that `version` equals `1.0`.
    2. GET `profiles/${CONNECTION_ID}/engage-gate` — `_check C3` that `allowed` is `false` and that `message` equals the refusal string character for character.
    3. PUT `profiles/${CONNECTION_ID}/ai-settings` with `{"conduct_rules":"","approach_guidance":"","ai_settings":{"model_name":"","call_cap":null,"disengage_threshold":null}}`, then GET the same path — `_check C1` that the GET returns empty strings and JSON `null` for call cap and threshold (not `0`, not a substituted model name), and `_check C1` that the `ai_settings` object has exactly the three keys `model_name`, `call_cap`, `disengage_threshold`.
    4. PUT `profiles/${CONNECTION_ID}/ai-settings` with conduct rules of 20001 characters (build with `printf 'x%.0s' $(seq 1 20001)`) — `_check C1` that the status is `400` and the body equals `{"error":"Conduct rules must be 20000 characters or less"}`.
    5. PUT `profiles/${CONNECTION_ID}/ai-settings` with a body that also carries `"policy_accepted_at":"2020-01-01T00:00:00Z"` and `"policy_version_accepted":"9.9"`, then GET `profiles/${CONNECTION_ID}/policy` — `_check C4` that `accepted` is still `false` and `accepted_version` is still null. This is the acceptance-forgery check.
    6. POST `profiles/${CONNECTION_ID}/policy/accept` — `_check C4` that `accepted` is `true`, `accepted_version` equals `1.0`, and `accepted_at` is a non-empty timestamp. Capture the timestamp in a variable.
    7. POST `profiles/${CONNECTION_ID}/policy/accept` again — `_check C4` that `accepted_at` equals the timestamp captured in step 6 and `accepted_version` is still `1.0`. One-time acceptance, proven by two calls.
    8. GET `profiles/${CONNECTION_ID}/engage-gate` — `_check C3` that `allowed` is `true` and that `message` is absent or empty.
    9. PUT `profiles/${CONNECTION_ID}/ai-settings` with populated values (`conduct_rules` `no PKing`, `approach_guidance` `level cautiously`, `model_name` `gemini-2.5-pro`, `call_cap` 25, `disengage_threshold` 2), then GET — `_check C2` that every value comes back identical.
    10. GET `profiles/${CONNECTION_ID}/timers`, PUT that exact body straight back unchanged, then GET `profiles/${CONNECTION_ID}/ai-settings` — `_check C2` that all five AI values from step 9 are still present. This is the non-interference check that no unit test can reach.

    Finish with a summary block: a line per criterion (`C1`, `C2`, `C3`, `C4`) reading `PASS` only when every check carrying that label passed, then `TOTAL CHECKS: n  FAILURES: m`. Exit `0` when the failure counter is zero and `1` otherwise, so the script is usable as a gate as well as a report.
